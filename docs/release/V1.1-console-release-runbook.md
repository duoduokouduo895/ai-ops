# AIDiag V1.1 Console 发布手册

## 1. 当前边界

V1.1 本地实现包含持久化浏览器 Session、只读 Console API、Git 版本化 Service Catalog、AIDiag 自监控、
Alertmanager 重启对账与 `frontend-console`。本手册只描述待确认的生产动作；执行本地测试不代表已经发布。

- 基础 `compose.yaml` 保持 Console 关闭，现有 V1 不依赖新增 Secret；
- `compose.console.yaml` 是显式激活层，缺少 BCrypt hash 或 audit pepper 时后端 fail-closed；
- AIDiag 仍只绑定 `127.0.0.1:18080`，Nginx 只转发 `/api/v1/console/**`；
- Pages 仅托管静态文件，浏览器不会接触 Basic Auth、数据库密码、模型 Key 或其他后端 Secret；
- 告警对账首次发布必须使用 `AIDIAG_RECONCILIATION_APPLY_TRANSITIONS=false` 观察漂移，不自动修改 Incident。
- Catalog 中的 Grafana 深链接默认指向 `http://127.0.0.1:13000`，只有本机 SSH tunnel 已建立时才可用；
  这不会公开 Grafana，也不会影响 Console 的 Incident、Evidence 和 Report 页面。

## 2. 用户需要在 GCP 执行的准备

以下命令会修改云端文件或 systemd 状态，必须在发布确认后逐步执行。

1. 在当前 AIDiag Secret 目录创建两个文件，不在 shell history 中写明文密码：

   ```bash
   umask 027
   read -rsp 'Console password: ' CONSOLE_PASSWORD; echo
   printf '%s' "$CONSOLE_PASSWORD" | htpasswd -niBC 12 aidiag-admin | cut -d: -f2 > aidiag_console_password_hash
   unset CONSOLE_PASSWORD
   openssl rand -base64 48 | tr -d '\n' > aidiag_console_audit_pepper
   chown root:10001 aidiag_console_password_hash aidiag_console_audit_pepper
   chmod 640 aidiag_console_password_hash aidiag_console_audit_pepper
   ```

2. 复制并检查 Nginx 配置。证书路径必须与 `certbot certificates` 的实际输出一致；此时只验证，不 reload：

   ```bash
   install -o root -g root -m 644 infra/nginx/ops-api.conf.example /etc/nginx/sites-available/ops-api.dduo.me.conf
   ln -s /etc/nginx/sites-available/ops-api.dduo.me.conf /etc/nginx/sites-enabled/ops-api.dduo.me.conf
   nginx -t
   ```

3. 安装续期 deploy hook 并验证计时器：

   ```bash
   install -o root -g root -m 750 infra/nginx/certbot-nginx-deploy-hook.sh \
     /etc/letsencrypt/renewal-hooks/deploy/20-nginx-reload
   systemctl enable --now certbot.timer
   certbot renew --dry-run
   systemctl list-timers certbot.timer --no-pager
   ```

4. 执行只读发布门禁：

   ```bash
   bash ./scripts/cloud-verify-v1-1-readiness.sh /opt/aidiag/releases/<release> /opt/aidiag/shared/secrets
   ```

   必须输出 `READINESS mutation=none`。磁盘使用率达到 85% 时禁止发布；清理镜像或 release 仍需单独确认，
   且至少保留当前与上一份可启动 release。

## 3. 发布与回滚顺序

收到单独发布确认后：

1. 使用 `docker compose -f compose.yaml -f compose.console.yaml config` 生成并人工审查合并配置；
   `AIDIAG_IMAGE` 与 `AIDIAG_RELEASE_VERSION` 必须替换为本次唯一 release 标识，禁止复用已发布 tag；
2. 先备份 PostgreSQL，再执行包含 V9/V10 的新后端迁移；
3. 只启动 AIDiag 后端，验证旧 Webhook、Read API、Stage 4 Basic Auth 未回归；
   随后执行 `bash ./scripts/cloud-verify-aidiag-startup.sh /opt/aidiag/releases/<release>`，必须确认非 root JVM
   已创建文件日志、文件归属 UID 10001、启动完成事件已写入且控制台没有日志路径权限异常；
4. 安装 Nginx server block，执行 `nginx -t && systemctl reload nginx`；
5. 验证未登录 401、错误 Origin 403、Cookie 属性、CSRF 注销和 CORS；
6. 发布 Pages，再配置 `ops.dduo.me`，最后进行 Desktop/Mobile Casefile 验收；
7. 对账先只读观察至少一个完整 firing/resolved 周期，再决定是否单独启用状态转换。

回滚时先恢复上一后端 release 与 Nginx 配置，再处理数据库。V9/V10 为新增表，不改变现有业务表语义；
回滚应用时保留新表，不在故障窗口执行 `DROP TABLE`。Pages 可独立回滚到上一 deployment。

## 4. Secret 轮换

Console 密码 hash 与 audit pepper 不同时轮换：

1. 先轮换密码 hash，重建后端并验证新密码；
2. 再轮换 audit pepper，重建后端；已有 CSRF token 会失效，但 Session 可通过 `GET /session` 获取新 token；
3. 强制所有会话退出需要显式更新 `console_session.revoked_at`，属于生产数据变更，必须另行确认；
4. 每次记录新 Secret 生效、旧值撤销、登录/注销验证与回滚文件，禁止记录 Secret 内容。

## 5. 未完成即不得发布的验收项

- 云端 PostgreSQL V9/V10 迁移与 Session 重启恢复；
- Certbot dry-run 与 deploy hook；
- Nginx 精确路径、TLS、CORS 和 Cookie 浏览器验证；
- Fault Lab firing → Incident → evidence → report → resolved 重放；
- 真实 GCP API 下的 Lighthouse/Core Web Vitals。当前本地没有 Chrome DevTools MCP，只能完成 bundle、Vitest 与
  Playwright 门禁，不能把本地估计值冒充线上 LCP/INP/CLS。
