## 0. 先记住的 90 秒项目介绍

我完成了一个由 AI-chat 和 AIDiag 组成的个人展示项目。

AI-chat 是支持 SSE 流式对话、知识库上传和 RAG 检索的 Java 服务；它使用 WebFlux、R2DBC、MySQL、Redis、RabbitMQ、Elasticsearch 与 Nacos。文档处理采用事务 Outbox 和消息确认，解决“数据库写入成功但消息没有可靠投递”的一致性风险。

AIDiag 是与业务解耦的证据驱动诊断平台。它通过 Prometheus、Loki、Tempo 收集 AI-chat 的指标、脱敏日志和 Trace；Alertmanager 触发告警后，平台将重复告警聚合为 Incident，后台 Worker 持久化采集证据，并在规则满足时生成可审计的诊断报告。AI 模型只给受限建议，不能执行命令或覆盖确定性结论。

部署上，前端托管在 Cloudflare Pages；AI-chat 和 AIDiag 已迁移到家庭 Ubuntu 主机，以 Docker 运行。Cloudflare Tunnel 提供公网业务入口，阿里云 FRP 主要保留远程 SSH 管理；对外可达性与内部依赖均有独立探针监控。

## 1. 两个项目分别解决什么问题？

| 项目 | 原始问题 | 交付的能力 | 不能夸大的边界 |
|---|---|---|---|
| AI-chat | 用户需要基于知识库进行流式 AI 问答；上传、索引与检索链路需要可恢复 | SSE 对话、文档上传、OSS、RAG、检索、异步文档处理 | 个人展示规模，不宣称高并发或大规模真实用户 |
| AIDiag | 聊天慢或失败时，仅靠页面与零散日志很难定位根因 | 告警、Incident、Metric/Log/Trace 证据、诊断报告、受限 AI 建议 | 不自动修复；证据不足时必须弃权；不是企业级 SOC 平台 |

### 两者如何连接？

```text
用户
  │
  ▼
Cloudflare Pages ──► AI-chat API（Cloudflare Tunnel）
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   Prometheus          Alloy              OTel
   指标采集         脱敏日志采集          Trace
        │                 │                 │
        ▼                 ▼                 ▼
 Alertmanager          Loki              Tempo
        │
        ▼
 AIDiag Webhook → Incident → 持久化 Worker → Evidence → Report
```

**关键解耦：** AI-chat 不调用 AIDiag 的业务接口，所以 AIDiag 故障不会阻断聊天主链。反过来，AI-chat 应用挂掉时，独立 Grafana / AIDiag Console 和 Blackbox 探针仍可以帮助区分应用故障、依赖故障与公网入口故障。若整台家庭主机或家庭网络离线，控制台会显示控制面不可达，外部探针才是确认主机级故障的证据。

## 2. 先掌握组件“为什么存在”

| 组件 | 为什么仅靠别的组件不够 | 在项目中的职责 |
|---|---|---|
| Prometheus | 日志不适合持续计算 P95、错误率、队列积压等数值趋势 | 采集指标、计算规则、触发告警 |
| Loki | 指标告诉你“异常”，但很难告诉你错误上下文 | 保存脱敏运维日志并按时间窗口取证 |
| Tempo | 日志难以还原一次请求跨服务的耗时路径 | 关联请求链路、定位慢在模型或下游依赖 |
| Alertmanager | Prometheus 不应直接把每次阈值变化变成重复任务 | 分组、去重、静默、将 firing/resolved 推送给 AIDiag |
| PostgreSQL | 内存队列在重启时会丢任务 | 保存 Incident、诊断任务、证据与报告，支持恢复 |
| Worker + Lease | Webhook 处理时做远程查询会慢且易超时 | 异步领取任务；租约、心跳与 fencing token 防止重复执行 |
| Docker Compose | 手工安装和版本漂移会让环境不可复现 | 把应用和中间件按镜像、网络、卷和资源限制声明化 |
| Cloudflare Tunnel | 家庭网络通常没有稳定公网 IP，直接端口暴露风险高 | 主机主动出站建隧道，向公网安全发布 API |

## 3. AIDiag 的一条真实故障链

以“模型调用超时”为例：

1. AI-chat 的模型请求变慢，指标中的超时数或 TTFT/P95 延迟上升。
2. Prometheus 规则在固定时间窗口内判定阈值命中。
3. Alertmanager 发送 `firing` Webhook；AIDiag 校验认证、限制请求体、按唯一约束幂等写入/更新 Incident。
4. `DiagnosisRunWorker` 从 PostgreSQL 领取任务。它使用租约避免多个实例同时执行同一个任务；崩溃后任务可被重新领取。
5. `TelemetryEvidenceCollector` 只执行受控的 PromQL、LogQL、TraceQL 模板，收集指标、日志、Trace 摘要。
6. `RuleBasedDiagnosisService` 判断规则：必要的 Metric 与 Log 证据成立，才写入主要根因；否则返回 `ABSTAIN`，而不是猜测。
7. Incident 被 `resolved` 后，系统更新生命周期并保留审计证据。可选的 DeepSeek 只基于脱敏、限量摘要生成建议。

### 这一链路的面试重点

- **为什么 Webhook 不直接做诊断？** 外部查询耗时且会失败；应尽快持久化事件，再异步处理。
- **为什么需要幂等？** Alertmanager 会重试，同一告警可能多次送达；重复创建 Incident/任务会污染诊断结果。
- **为什么租约而不是简单定时任务？** 服务重启、并发实例、任务卡死时需要接管和恢复。
- **为什么 AI 不能直接下结论？** 模型可能幻觉；确定性规则与原始证据才是可审计依据。

## 4. AI-chat 的一条关键可靠性链

以“知识库上传后异步处理”为例：

1. 用户上传文档，服务完成校验、元数据与业务状态写入。
2. 在同一个 R2DBC 事务内写入 Outbox 记录，而不是先写数据库再“希望 RabbitMQ 发送成功”。
3. 后台发布者读取待发送 Outbox，向 RabbitMQ 发布，并等待 publisher confirm。
4. 消息消费者执行解析、切分、向量化/索引等耗时工作。
5. 发生重试时按 **at-least-once** 设计：消费者与业务写入必须考虑幂等，不能宣称 exactly-once。

### 这一链路的面试重点

- **Outbox 解决什么？** 解决数据库事务和消息发送之间无法天然原子提交的问题。
- **为什么仍可能重复？** 发布超时或确认丢失时，生产者会重试；因此它保证的是至少一次投递，不是恰好一次。
- **WebFlux 的注意点？** 不能在事件循环中执行阻塞 JDBC、文件解析或长时间模型调用；阻塞工作要隔离线程池或异步化。

## 5. 当前部署地图：你真正运行的是什么

```text
浏览器
 ├─ app.dduo.me  → Cloudflare Pages → 前端
 ├─ api.dduo.me  → Cloudflare Tunnel → 家庭主机 127.0.0.1:18083（AI-chat）
 ├─ ops.dduo.me  → Cloudflare Pages → AIDiag Console
 └─ ops-api.dduo.me → Cloudflare Tunnel → 家庭主机 127.0.0.1:18080（AIDiag）

远程 SSH：你的电脑 → 阿里云 FRP → 家庭主机 SSH
```

安全边界：AI-chat、AIDiag 与中间件优先绑定在本机/私有 Docker 网络；UFW 默认拒绝入站；SSH 禁用 root 与密码登录，只接受个人密钥。阿里云 FRP 是管理跳板，不承载正常用户业务流量。

## 10. 每次复习的固定回答结构

面对任意技术问题，按下面四句话组织：

1. **问题：** 当时什么会失败或不可控？
2. **方案：** 我用什么机制解决，为什么不用更简单的方案？
3. **取舍：** 方案仍有哪些成本、边界或风险？
4. **验证：** 我如何证明它真的有效，而不是只写了代码？

例如：

> 文档入库时，数据库写成功但消息发送失败会导致数据与异步任务不一致。我在同一事务内写入 Outbox，再由后台发布并等待 RabbitMQ confirm。它仍是至少一次投递，所以消费者必须幂等。通过受控失败、重试和最终索引结果验证链路可恢复。
