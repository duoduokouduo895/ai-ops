# Stage 5.4 独立故障入口验证记录（2026-07-13）

## 结论

Stage 5.4 的主救援入口已从 AI-chat Admin 中拆出。云端 release `20260713-stage5-4-3` 已运行独立 Blackbox 探针和 Grafana Dashboard；AI-chat Admin 只保留为服务存活时的辅助入口。该设计能覆盖 AI-chat JVM 未启动和中间件网络不可达，但不能覆盖整台 GCP 主机或同机监控平面失联。

## 已验证内容

- AIDiag 未认证只读 API 返回 `401`，文件型凭据认证的 shadow summary 返回 `200`，越界分页返回 `400`，响应 JSON 字段完整；浏览器不持有该凭据；
- Blackbox Exporter `v0.28.0` 使用 digest 固定镜像，未映射宿主机端口；Prometheus 与 Blackbox 同样不直接暴露公网；
- `application`、`mysql`、`redis`、`rabbitmq`、`elasticsearch`、`nacos` 六个 `probe_success` 序列均存在且当前为 `1`；
- Grafana 已 provision `ai-chat-break-glass`（“AI-chat 独立故障入口”）和原 Stage 5 Operations Dashboard；
- Prometheus 与 Grafana 的 bind mount 源均已确认指向 `/opt/aidiag/releases/20260713-stage5-4-3`，不再引用稳定软链接的旧目标；
- AIDiag 本地与云端构建均包含真实 Spring Bean 装配测试，防止只通过直接构造对象而漏掉容器启动错误。

## 发布中发现并修复的问题

1. 首次激活时 `ReadApiAuthenticator` 存在两个构造器但未明确注入入口，单元测试通过、生产 Spring Context 启动失败。健康门禁阻止切换；随后增加 `@Autowired` 和 `ApplicationContextRunner` 回归测试。
2. 原回滚流程恢复了 release 软链接，但共享的本地镜像标签仍指向失败版本，导致旧目录启动新镜像。已改为回滚时从旧 release 重建镜像。
3. Compose 曾以稳定 `current` 软链接作为 project directory，Docker 继续挂载旧 release 的 Prometheus/Grafana 配置。已改为使用不可变真实 release 路径；当前云端 Prometheus/Grafana 已强制重建并验证新配置生效。
4. `size=101` 最初被 Bean Validation 拦截后返回 `500`。已移除 Controller 级 AOP 校验，使用 Spring MVC 原生方法校验，并增加“返回 400 且不查询数据库”的测试；云端补丁 release 已验证返回 `400`。

## 边界与后续

- TCP 探针成功仅表示 DNS、路由和端口连接成功，不证明账号密码、协议命令、数据正确性或性能正常；
- Alloy 当前主要读取应用文件日志。JVM 若在 logger 初始化前失败，仍需从受限 Docker 日志采集链补启动证据；不得直接向业务容器开放原始 Docker socket；
- Grafana 与被监控项目同机。如果主机、Docker daemon、磁盘或主机网络整体故障，需要外部 uptime/GCP Monitoring 产生第二条独立信号；
- Admin BFF 与前端仍需使用真实 ADMIN 登录完成一次端到端验收，且它不是启动失败时的救援入口。
