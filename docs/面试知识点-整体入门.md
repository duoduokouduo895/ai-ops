## 0. 开口 90 秒（先练这个）

我做了一个个人展示项目，包含两个解耦的部分。

**AI-chat** 是一个 Java 聊天服务：支持流式对话、知识库上传和检索。上传文档后，解析和索引走后台消息，避免把慢活堵在用户请求里。

**AIDiag** 是独立的诊断平台。聊天服务不调用它。AI-chat 只对外暴露指标、脱敏日志和调用链；Prometheus 发现异常后，Alertmanager 把告警推给 AIDiag。AIDiag 把重复告警收成一个故障事件，后台任务去查指标、日志、Trace，用固定规则写诊断报告。大模型只给建议，不能改结论，也不能执行修复。

部署在家庭 Ubuntu 主机的 Docker 里。前端在 Cloudflare Pages，API 经 Cloudflare Tunnel 进本机 loopback。阿里云 FRP 只用来 SSH 维护，不走用户流量。这是个人展示规模，不是企业级高可用。

面试官如果只给你 30 秒，就压成三句话：

1. 我给自己的聊天服务做了一个**证据驱动**的诊断闭环。
2. 告警进系统后会**幂等去重、异步取证、规则下结论**。
3. AI 只能基于已有证据给建议，证据不够就**弃权**。

## 1. 先搞清：这个仓库到底有什么

这个 Git 仓库的主体是 **AIDiag**（本仓库的 Java 后端 + Vue 控制台 + 观测配置）。**AI-chat** 是被监控的业务，代码不在这个仓库里，但接入契约写在 `docs/AI-chat-接入指南.md`。

可以把它想成医院：

| 角色 | 项目里是谁 | 一句话 |
|---|---|---|
| 病人 | AI-chat | 真正给用户聊天的服务 |
| 体温计 / 心电图 | Prometheus 指标 | 数字是否异常 |
| 病历文字 | Loki 日志 | 当时程序记下了什么 |
| 出诊路线图 | Tempo Trace | 一次请求慢在哪一段 |
| 分诊台 | Alertmanager | 把“持续异常”变成告警通知 |
| 档案室 + 办案员 | AIDiag + PostgreSQL | 建故障单、取证、写报告 |
| 会诊专家（受限） | DeepSeek via Spring AI | 只能看摘要给建议 |
| 只读病案室 | Vue3 Console | 给人看状态、故障、证据 |

**最重要的解耦：** AI-chat 的登录、聊天、知识库主链**不调用** AIDiag。AIDiag 挂了，聊天还应能继续；聊天挂了，独立探针和 Grafana 仍可帮你区分“应用死了 / 依赖死了 / 公网入口死了”。

整台家庭电脑断电或家里断网时，AIDiag 自己也一起消失，**不能自报整机故障**。这必须靠外部探针（例如 Cloudflare / 异地探测）。面试被问“高可用了吗？”直接说：没有，同机观测栈有这个硬边界。

## 2. 技术名词小词典（用生活类比）

### 2.1 HTTP 和 Webhook

普通 API：浏览器问服务器“给我数据”。

**Webhook** 反过来：Alertmanager 发现告警后，**主动 POST** 一段 JSON 到 AIDiag 的 `/api/v1/alerts/alertmanager`。

类比：不是你天天刷新快递柜，而是快递柜短信通知你。

面试要补一句：Webhook 必须鉴权（本项目是 Basic Auth）、限制体积、尽快落库。不能在 Webhook 线程里去查 Prometheus/Loki，因为外部查询慢、会超时，Alertmanager 还会重试。

### 2.2 幂等（idempotent）

同一请求做 1 次和做 100 次，**业务结果一样**。

Alertmanager 保证的是“至少送到一次”，网络抖动会重发。如果每次 POST 都新建故障单，同一个超时就会变成 20 个 Incident。

本项目用 PostgreSQL **唯一约束** 挡住重复插入，而不是只靠 Java 里的 `if`。原因：两个请求可能同时到达两台/两个线程，内存判断会同时认为“还没有”。

### 2.3 唯一约束 / 部分唯一索引

表上规定某几列组合不能重复。数据库在并发下也能挡住第二行。

`alert_event`：`(receiver, group_key, fingerprint, alert_status, starts_at)` 唯一。

`incident` 还有**部分唯一索引**：同一个 `correlation_key`，在 `OPEN/DIAGNOSING/DIAGNOSED/FAILED` 这些“还活着”的状态里只能有一条。历史已 `RESOLVED` 的可以再出现新的一轮故障。

### 2.4 Metric / Log / Trace

| 信号 | 回答什么 | 不够的时候会怎样 |
|---|---|---|
| Metric | 超时数、延迟、积压是否越过阈值 | 只知道“坏了”，不知道上下文 |
| Log | 某类脱敏事件有没有出现 | 没有趋势，也不好算 P95 |
| Trace | 一次请求卡在模型、数据库还是消息 | 单独命中不能当主根因 |

本项目规定：**Metric 和 Log 同时命中**才能写主要根因；只有 Trace 或只中一类，最多算弱支持；都没有就 `ABSTAIN`（弃权）。

### 2.5 PromQL / LogQL / TraceQL

三种查询语言，分别问 Prometheus、Loki、Tempo。

关键设计：**查询模板写死在服务端规则里**，告警的 annotation 文本不能拼进查询。否则恶意或脏数据可能变成任意查询（查询注入）。

### 2.6 租约（lease）和 fencing token

后台 Worker 从数据库“领任务”，不是从内存队列。

- **租约**：我领了这个任务，在 `lease_until` 之前归我；过期别人可以接手。
- **心跳**：干活过程中不断续租，证明我还活着。
- **fencing token（本项目是 `lease_token`）**：每次领取换新令牌。旧 Worker 醒过来想写库时，`WHERE lease_token = 旧值` 对不上，写失败。这就叫“防止僵尸 Worker 覆盖新结果”。

`FOR UPDATE SKIP LOCKED`：多个 Worker 同时抢任务时，已锁的行直接跳过，不会互相堵死。

### 2.7 事务 Outbox（AI-chat 侧，整体介绍时用）

数据库提交和发 RabbitMQ 消息**不能天然一起成功或一起失败**。

做法：同一事务里写业务状态 + 一张 Outbox 待发送表；后台再发消息并等 broker 确认。这样重启后还能把没发出去的补发出去。

它保证的是 **至少一次**，不是恰好一次。所以消费端必须幂等。

### 2.8 SSE

Server-Sent Events：服务器单向持续推文字，聊天打字机效果常用它。和 WebSocket 的差别：SSE 主要是服务器→浏览器的流，实现更简单；本项目面试若被问到 AI-chat，说到流式输出即可，不必夸成实时双向通信。

### 2.9 Docker Compose

用 YAML 声明“要哪些容器、哪个镜像、连哪张网、挂哪个卷、资源上限多少”。好处是环境可复现。本项目镜像版本和 digest 锁在 `versions.env`，避免 `latest` 漂版本。

### 2.10 Cloudflare Tunnel vs FRP

家庭电脑通常没有稳定公网 IP，也不该把 22/8080 直接暴露。

- **Cloudflare Tunnel**：主机主动出站建隧道，把 `api.dduo.me` / `ops-api.dduo.me` 转到本机 `127.0.0.1`。这是**用户业务入口**。
- **FRP**：经阿里云跳板做 **SSH 维护**，不承载聊天或诊断流量。

## 4. AIDiag 一条故障链（模型超时为例）

用这个故事贯穿整场面试。

1. 用户聊天时模型迟迟不返回。AI-chat 把这次请求记为 `outcome=timeout`，并写一条脱敏运维日志 `ai_chat_stream_finished/timeout`，Trace 上也能看到超长 span。
2. Prometheus 规则 `AiChatModelTimeout`：5 分钟窗口内 timeout 次数超过阈值，且持续一段时间（`for`），才变成告警。这是为了避免毛刺。
3. Alertmanager 把同一组告警合成一个 group，状态先是 `firing`，恢复后发 `resolved`。
4. AIDiag Controller 校验 Basic Auth，最多读固定字节，拒绝超大包。Service 递归脱敏，原文只存 SHA-256。
5. `INSERT ... ON CONFLICT DO NOTHING` 写入 `alert_event`。冲突则 `receive_count+1`，不新建 Incident。
6. firing 按 `SHA-256(environment + receiver + groupKey)` 聚合到**一个活动 Incident**；第一次会创建 `diagnosis_run(attempt=1, PENDING)`。
7. `DiagnosisRunWorker` 用 `FOR UPDATE SKIP LOCKED` 领取，状态 `LEASED → COLLECTING → EVIDENCE_READY`。
8. `DiagnosisWorker` 按精确 `(serviceName, alertName)` 找到规则，分别查 Prometheus / Loki / Tempo。查询有超时、响应大小、条数上限；每次查询前续租。
9. 只有 Metric 和 Log 都命中，才把候选标成 `SUPPORTED` 并允许作为主要根因。数据库触发器再挡一层：非 `SUPPORTED` 不能写进 `diagnosis_report.primary_root_cause_id`。
10. Alertmanager 的 resolved 到来后，若时间顺序安全，Incident 变为 `RESOLVED`，证据和报告保留。
11. 运维若手动点 AI 建议：模型只看到脱敏摘要和允许的 runbook action；输出必须是指定 JSON，且 evidence id / action 必须在白名单内。建议写入 `ai_diagnosis_attempt`，**绝不改** `diagnosis_report`。

### 这条链上面试官最爱追的四个“为什么”

**为什么 Webhook 不直接诊断？**  
外部查询 8 秒超时都可能发生；Alertmanager 等不及。先落库，再异步。

**为什么要幂等？**  
重试、重复通知、进程重启都会让同一条 firing 再来。重复建单会让“一次故障”变成一堆垃圾事件。

**为什么要租约而不是 `@Scheduled` 直接干？**  
定时任务在多实例、崩溃、卡死时要么丢任务要么双跑。租约把“谁在跑、能不能接管”写进数据库。

**为什么 AI 不能下结论？**  
模型会幻觉，还可能把秘密复述出来。可审计的是规则 + 原始证据。AI 是附加层。

## 5. AI-chat 你需要知道的下限

简历如果只写 AIDiag，也要能解释被监控对象，否则观测链是空的。

AI-chat 技术栈（与 AIDiag 不同）：WebFlux、R2DBC、MySQL、Redis、RabbitMQ、Elasticsearch、Nacos、LangChain4j。它是**响应式/非阻塞**服务：不要在事件循环线程里跑 JDBC、大文件解析、同步死等模型。

四个被诊断场景对应四条告警：

| 告警 | 业务含义 | 典型证据方向 |
|---|---|---|
| `AiChatModelTimeout` | 模型流超时 | timeout 计数 + 超时结束日志 |
| `AiChatR2dbcPoolExhaustion` | 数据库连接拿不到 | pending 连接 + acquire timeout 日志 |
| `AiChatDocumentBacklog` | 文档 Outbox 积压 | pending 数量 + dispatch retry 日志 |
| `AiChatSearchUnavailable` | RAG/ES 搜索失败 | search error 计数 + knowledge_search error 日志 |

隐私红线（一定要主动讲）：指标标签和运维日志**不含** Prompt、回答、userId、conversationId、Authorization、Cookie、Secret。

## 6. 部署、安全、诚实边界

### 6.1 当前运行位置

以仓库文档和家庭部署契约为准：AI-chat 与 AIDiag 在家庭 Ubuntu + Docker。历史文档会提到 GCP，那是迁出前的生产。面试时说：

> 我做过云主机部署，后来迁到家庭服务器。当前公网入口是 Cloudflare Tunnel，SSH 走 FRP。如果被问“现在到底跑在哪”，以家庭主机的只读检查为准，不以 README 里过期的 GCP 句子为准。

### 6.2 安全可以讲的点（不要夸成安全专家）

- 中间件和 management 端口绑 `127.0.0.1`，UFW 默认拒绝入站。
- Secret 不进 Git、镜像、环境变量和日志。
- Webhook 有鉴权、大小限制、脱敏。
- Console：HttpOnly / Secure / SameSite=Strict Cookie，Session 只存 hash，CSRF 绑定 Session，失败锁定，响应 `Cache-Control: no-store`。
- SSH 禁 root、禁密码，只用个人密钥。

### 6.3 绝对不要说的话

- “企业级高可用 / 生产准确率 100%”
- “AI 自动修复 / Agent 自己改服务器”
- “exactly-once 消息”
- “我们能诊断任意未知故障”
- “同机监控可以发现整机断电”

正确说法模板：

- 个人展示和受控实验闭环。
- 至少一次投递 + 幂等。
- 证据不足就弃权。
- AI 是受限建议。
- 整机故障靠外部 sentinel。

## 8. 高频题（先自己答，再对答案要点）

### Q1. 介绍一下项目？

用第 0 节。卡在 90 秒内。接着等面试官追问，不要自己把 Outbox、FRP、Vue 一次倒完。

### Q2. Spring Boot 在这里干什么？

AIDiag 是模块化单体：Controller 接 Webhook/Console API，Service 做业务，JdbcTemplate 写 PostgreSQL，`@Scheduled` Worker 轮询任务，Micrometer 暴露自身指标，Flyway 管迁移。它不是微服务拆分，也不是 WebFlux。

### Q3. 为什么选 PostgreSQL 而不是 Redis 做任务队列？

任务、租约、证据、报告需要**重启仍在**，还需要事务和约束。Redis 适合缓存和短生命周期队列；本项目要审计和恢复，数据库更合适。家庭单机也减少运维组件。

### Q4. Prometheus 和 Grafana 有什么区别？

Prometheus 负责采集、存储时间序列、按规则告警。Grafana 负责把多个数据源画成图给人看。Grafana 不替代告警管道，也不替代 AIDiag 的故障单。

### Q5. Docker Compose 解决什么？

把 AIDiag、PostgreSQL、Prometheus、Loki、Tempo、Grafana、Alertmanager 的版本、网络、卷声明化。面试可提：`docker compose config --quiet` 和 `promtool check rules` 是发布前检查，不是“我在服务器上手工装了一堆软件”。

### Q6. 证据不足为什么必须弃权？

运维结论会被人拿去重启服务或改配置。没有独立证据就写“根因是某某”，比不诊断更危险。弃权会在报告 limitations 里写清楚缺了什么。

### Q7. 如果 Prometheus 挂了怎么办？

Stage3 查询失败会记采集失败，不能凑 `SUPPORTED`。应用本身若还在，聊天可能仍可用。要用 Blackbox / 外部探针区分“指标系统挂了”和“业务挂了”。不要说“我们有完善的监控高可用”。

### Q8. Vue 页面为什么是只读的？

产品定位是调查和展示，不是执行修复。只读减少误操作，也避免把“重启按钮”做进个人项目里让面试官以为你在生产乱执行。

### Q9. 你怎么验证过？

可以说：仓库有 Stage 0～5 的验证记录和 Fault Lab 受控故障；规则针对隔离实验有 Ground Truth。同时主动说：样本不是真实云厂商/磁盘损坏，**不宣称生产准确率**。

### Q10. 最大的技术难点是什么？

推荐答：**告警重试 + 进程重启 + 并发 Worker** 下，既不丢任务也不重复诊断、不被旧 Worker 覆盖。难点不在“接了 DeepSeek”。
