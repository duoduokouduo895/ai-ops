# 其他项目接入 AIDiag 指南

## 1. 先判断要接到哪一层

AIDiag 接入分为三种深度，不应一开始就修改诊断代码：

| 层级 | 能力 | 是否需要修改 AIDiag Java 代码 |
|---|---|---|
| L1 可达性监控 | HTTP/TCP probe、Grafana、基础告警 | 不需要；增加受控 target/config |
| L2 三信号可观测 | Metrics、脱敏 Logs、Traces、通用告警 | 通常不需要；增加采集和规则配置 |
| L3 确定性诊断 | Incident、固定查询、多证据、根因报告 | V1 需要新增 `DiagnosisRuleProvider`；V1.1 计划配置驱动 |

如果项目只是想知道“能不能访问、哪个依赖端口不通”，先做 L1。只有明确了可测量的故障契约和独立证据，才进入 L3。

## 2. V1 当前真实边界

V1 的生产 target 已使用 Prometheus `file_sd`，接入地址可以配置；但确定性诊断规则仍在 Java Provider 中版本化。也就是说：

- 新增监控目标不必修改被监控项目的业务逻辑；
- 被监控项目仍需要输出符合契约的 Metrics/Logs/Traces；
- 若要生成新的主要根因，需要新增规则 Provider、测试、Prometheus alert 和 Dashboard，然后发布 AIDiag；
- 不能宣称“任何项目只填一个 URL 就能自动诊断”。

## 3. 接入前必须回答的问题

1. 服务唯一名是什么？不同环境是否有独立名字？
2. 哪个 URL 能表示应用进程健康，是否与业务端口分离？
3. 依赖哪些数据库、缓存、消息队列、搜索和外部 Provider？
4. 哪些故障能用一个低基数 Metric 发现？
5. 哪个脱敏事件能作为第二类独立证据？
6. Trace 中哪个 span 属性能辅助定位，但不会包含用户数据？
7. 告警阈值和持续时间是什么，为什么？
8. 故障恢复如何确认，resolved 的时间语义是什么？
9. 能否在隔离环境稳定制造 Ground Truth？
10. 哪些数据绝不能进入 Loki、Tempo、PostgreSQL 和模型？

这些问题没有答案时，先做可观测性，不要直接写“AI 根因规则”。

## 4. 最小遥测契约

### 服务身份

统一使用安全、稳定、低基数的 `service_name`：

```text
<product>-<role>-<environment>
```

示例：`order-api-production`。允许字符为 `[A-Za-z0-9._-]`，不使用容器 id、Pod id、user id 或随机值。

Metrics、Logs、Traces 和 Alertmanager labels 中的 service identity 必须一致，否则 AIDiag 无法正确关联。

### Metrics

至少提供：

- `up` 或 management scrape 健康；
- 请求总数，固定 `outcome`；
- 请求延迟 histogram/timer；
- 活跃请求/线程/连接 gauge；
- 核心异步队列或 outbox backlog；
- 依赖失败 counter。

禁止把 URL 全路径、SQL、异常正文、userId、traceId、文件名和 Prompt 作为 label。

### Logs

使用独立的运维事件 logger，推荐字段：

```json
{
  "event": "dependency_operation_finished",
  "result": "timeout",
  "durationMs": 3000,
  "errorType": "TimeoutException",
  "traceId": "...",
  "spanId": "..."
}
```

不要记录请求正文、响应正文、Authorization、Cookie、Token、邮箱、手机号、用户或会话 id。`errorType` 使用异常类名或固定分类，不使用 `exception.getMessage()`。

### Traces

- 使用 OTel SDK/Agent 导出 OTLP；
- 设置稳定 `service.name`、deployment environment、service version；
- 只保留必要 span name 和低敏属性；
- 禁止采集聊天正文、SQL 参数、HTTP Authorization 和上传文件内容；
- Metrics/Logs exporter 若已有独立链路，应设为 `none`，避免重复。

## 5. L1 可达性接入步骤

1. 为应用提供独立 health URL；
2. 在 Blackbox 中选择固定 `http_health` 或 `tcp_connect` module；
3. 把 target 写入受控 file-SD，而不是开放任意用户 URL；
4. labels 至少包括 `service_name`、`component`、`target_kind`、`module`；
5. `target_kind` 区分 `application`、`dependency` 和 `ingress`；
6. 在 Prometheus 增加“持续失败”规则，不对单次抖动立即建单；
7. 在 Grafana 增加探针状态和排查顺序；
8. 用停止隔离实例/阻断隔离端口验证 firing 和 resolved。

file-SD 示例：

```json
[
  {
    "targets": ["order-api:9091"],
    "labels": {
      "scrape_kind": "metrics",
      "service_name": "order-api-production"
    }
  },
  {
    "targets": ["https://api.example.com/healthz"],
    "labels": {
      "scrape_kind": "probe",
      "module": "http_health",
      "component": "public-ingress",
      "target_kind": "ingress",
      "service_name": "order-api-production"
    }
  }
]
```

目标文件必须由部署脚本校验 URL、权限和 digest，不允许浏览器或外部告警直接提供任意 probe URL，避免 SSRF。

## 6. L2 三信号接入步骤

1. management metrics 使用私有端口或私有网络；
2. Prometheus 增加 scrape job 或 file-SD metrics target；
3. Alloy 增加只读日志 source，固定 `service_name/environment`；
4. 应用将 OTLP 发往 `alloy:4318`；
5. Grafana 配置 Prometheus/Loki/Tempo datasource 关联；
6. 发送一次无敏感数据的 smoke 请求；
7. 从 Metric 找到时间窗口，从 Log 找到 traceId，再在 Tempo 打开同一 Trace；
8. 执行隐私扫描，确认三类信号均不包含业务正文和 Secret。

## 7. L3 确定性诊断接入步骤

### 步骤 1：定义故障契约

每个候选故障必须有：

- 唯一 Alert name；
- 一个发现异常的 Metric + 阈值；
- 一个独立脱敏 Log marker；
- 可选 TraceQL；
- candidate name 和受控说明；
- 只读或需人工审批的 Runbook action；
- 隔离 Ground Truth 制造和恢复方法。

### 步骤 2：新增规则 Provider

实现 `DiagnosisRuleProvider`，返回固定 `DiagnosisRule`。不要读取 annotation 生成查询，不要提供任意表达式 API。

### 步骤 3：注册和冲突检查

`DiagnosisRuleRegistry` 会拒绝重复 `(serviceName, alertName)`。新增 production/candidate/lab 身份时需要显式注册，避免同一规则误查另一环境。

### 步骤 4：新增 Prometheus rule

规则必须保留 `service_name` label，设置合理 `for`，并在 annotations 中只写固定说明。Alertmanager `group_by` 应包含 `alertname/service_name/environment`。

### 步骤 5：新增测试

至少覆盖：

- Metric + Log 同时命中为 SUPPORTED；
- 任一缺失不能成为主要根因；
- Tempo 超时不阻断 P0 Metric/Log；
- 未知/注入 service/alert 不发起任何查询；
- 超大响应、非法 JSON、超时；
- candidate、production、lab 三种 identity 不串数据；
- firing、重复 delivery、resolved、延迟 resolved；
- 租约丢失时不持久化报告。

### 步骤 6：隔离评测

故障实验服务不得连接真实生产数据库、队列、搜索或模型。至少重复多轮，记录建单率、SUPPORTED/abstain、报告延迟、恢复率和失败样本。不能只保存最终成功截图。

## 8. V1.1 配置驱动设计

V1.1 建议引入经 JSON Schema 校验、Git 版本化的 service catalog：

```yaml
apiVersion: aidiag.dduo.me/v1alpha1
kind: MonitoredService
metadata:
  name: order-api-production
spec:
  environment: cloud-production
  metricsTarget: order-api:9091
  healthTargets:
    - kind: application
      url: http://order-api:9091/actuator/health
    - kind: ingress
      url: https://api.example.com/healthz
  rules:
    - alertName: OrderDownstreamTimeout
      metric:
        templateId: request-timeout-count-v1
        threshold: 1
      log:
        templateId: operation-timeout-event-v1
      trace:
        templateId: downstream-error-span-v1
      candidate: DOWNSTREAM_TIMEOUT
```

安全约束：

- 配置只能引用经过代码评审的 template id，不能提交任意 PromQL/LogQL/TraceQL；
- URL 只能使用允许的 scheme/host/network zone；
- schema 校验、唯一 service name、版本和签名是发布门禁；
- 配置变更也要经过 contract test 和隔离 Ground Truth，不因“无 Java 改动”而降低审查级别。

## 9. 接入验收清单

- [ ] service identity 在 Metrics/Logs/Traces/Alerts 一致
- [ ] management/OTLP/Prometheus/Loki/Tempo 不直接暴露公网
- [ ] 指标标签低基数且无个人信息
- [ ] 运维日志无正文、ID、Secret 和异常 message
- [ ] Trace 无敏感属性
- [ ] application/dependency/ingress probe 能区分故障层次
- [ ] duplicate Webhook 只产生一个 event/Incident/run
- [ ] Metric 或 Log 缺失时主动弃权
- [ ] resolved 不会关闭更新的 firing Incident
- [ ] Worker 崩溃后任务可被回收
- [ ] 租约过期的 Worker 无法回写
- [ ] 隔离故障多轮可重复，失败样本已归档
- [ ] 回滚不会删除数据库卷或制造双写
- [ ] 文档标明已实现、待发布和后续计划

## 10. 常见误区

- “端口能连”不等于依赖健康；
- “Trace 命中”不等于根因已确认；
- “接了大模型”不等于智能运维；
- “测试 20/20”不等于生产准确率 100%；
- “配置驱动”不等于允许任意查询和 URL；
- “应用 Admin 有运维页面”不能替代独立 Grafana 救援入口；
- “Docker 在云端”不需要让业务中间件端口直接暴露公网。
