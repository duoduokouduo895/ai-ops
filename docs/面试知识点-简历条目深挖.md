## 0. 把简历翻译成 45 秒（对上五条再开口）

我用 Spring Boot + PostgreSQL 做了一个告警诊断服务。Alertmanager 通过 Webhook 把告警推过来；我靠数据库唯一约束做幂等，同一条告警不会变成多个故障单。诊断任务也落在 PostgreSQL 里，用状态机和租约调度后台 Worker，服务重启能恢复，失败会重试，多个 Worker 不会抢同一条任务。Worker 按固定查询去 Prometheus、Loki、Tempo 取指标、日志和调用链，再用规则判断能不能确认根因。Spring AI 接入 DeepSeek 只生成建议：输入脱敏、输出校验、必须引用已有证据。前端是 Vue3 + TypeScript 的只读运维页，看服务状态、故障列表、报告和证据。

## 1. 技术栈：每个词在你项目里的真实角色

面试官常从技术栈扫到某一项就问“你用它干什么”。不要背官网简介。

| 技术 | 你项目里的角色 | 一句话证据 |
|---|---|---|
| Spring Boot | AIDiag 单体后端：Webhook、Console API、定时 Worker、Flyway、Micrometer | `AiDiagApplication`，`@RestController` + `@Scheduled` |
| PostgreSQL | 故障单、告警事件、任务租约、证据、报告、Session 的**系统 of record** | Flyway `V1`～`V10` |
| Prometheus | 抓指标、算规则、把异常变成告警；也被 AIDiag 用固定 PromQL 回查 | `infra/prometheus/` |
| Grafana | 给人看图的独立入口，不替代故障单 | `infra/grafana/dashboards/` |
| Docker Compose | 应用 + 中间件 + 观测栈声明式部署 | `compose.yaml`、`deployment/home/` |
| Spring AI | 仅 Stage4：把脱敏 JSON prompt 发给 DeepSeek，映射成 `AiDiagnosisAdvice` | `SpringAiAdvisoryModelClient` |
| Vue3 | 只读 Console：Inbox / Services / Incidents / Casefile | `frontend-console/` |

容易被追问的边界：

- **Spring Boot ≠ Spring Cloud。** AIDiag 没有把诊断拆成一堆微服务。
- **Prometheus ≠ Grafana。** 一个负责存序列和告警，一个负责可视化。
- **Spring AI ≠ 自动运维。** 没有 Tool Calling 去执行 Shell。
- **Vue3 页不能改故障状态、不能重启容器。**

如果被问 “PostgreSQL 为什么还装了 pgvector？”：表结构里预留了 runbook 切片向量字段，V1 主链**没有**靠向量检索来下诊断结论。诚实说“预留，主链是规则 + 遥测证据”。

## 2. 条目一：Alertmanager Webhook + 唯一约束 + 幂等接收

简历原文：

> 基于 Alertmanager Webhook 与 PostgreSQL 唯一约束设计告警处理流程，实现重复告警幂等接收，避免同一告警被重复创建为多个故障事件。

### 2.1 人话

监控系统会反复通知“还在超时”。我的服务必须把**同一条告警**认成同一件事：可以给计数 +1，但不能新开一堆故障单。

### 2.2 为什么必须做

Alertmanager 的 Webhook 是 **at-least-once**：超时、5xx、网络闪断都会重试。进程也可能在写入后、返回 202 前崩溃，于是再送一次。

如果用“先 SELECT 再 INSERT”：两个并发请求都看不到已有行，会插入两行。所以幂等要下沉到数据库约束。

### 2.3 项目怎么做

**入口** `AlertmanagerWebhookController`

1. Basic Auth，失败 401。
2. `Content-Length` 和实际读取都不超过 `maxPayloadBytes`（默认 256 KiB，上限 1 MiB）。
3. 只接受 JSON object。
4. 成功返回 **202 Accepted** 和收据（接受几条、重复几条、涉及哪些 Incident）。

**业务** `AlertmanagerWebhookService.accept`

1. 校验 receiver、groupKey、alerts、status、时间、severity、受控 label（`alertname` / `service_name` / `environment` 只允许 `[A-Za-z0-9._-]+`）。
2. 递归脱敏 password/token/Bearer/邮箱/手机号等；**原始 body 只留 SHA-256**。
3. 每条 alert 独立插入 `alert_event`：

```sql
INSERT INTO alert_event (...)
VALUES (...)
ON CONFLICT (receiver, group_key, fingerprint, alert_status, starts_at) DO NOTHING
RETURNING id
```

4. `DO NOTHING` 表示这是重复投递：`receive_count + 1`，**不**创建新 Incident。
5. `firing` 才 `upsert` 活动 Incident；`resolved` 只关闭时间顺序安全的活动 Incident。
6. 聚合键 `correlation_key = SHA-256(environment + receiver + groupKey)`，不用告警文本（文本会变，还可能含用户数据）。
7. 活动 Incident 靠部分唯一索引：

```sql
CREATE UNIQUE INDEX uq_incident_active_correlation
  ON incident (correlation_key)
  WHERE status IN ('OPEN', 'DIAGNOSING', 'DIAGNOSED', 'FAILED');
```

8. 首次 firing 创建 `diagnosis_run(attempt=1, INITIAL, PENDING)`，同样 `ON CONFLICT (incident_id, attempt) DO NOTHING`。
9. 新 firing 只能把 severity **抬高**（INFO→WARNING→CRITICAL），不能把 CRITICAL 降下去。

### 2.4 面试怎么答（建议背这个结构）

Alertmanager 会重试，所以接入层按幂等设计。我先鉴权、限流体积、脱敏，再按 `receiver + group_key + fingerprint + status + starts_at` 做唯一键。冲突时只增加接收次数。活动故障单按环境、receiver、groupKey 的哈希聚合，数据库部分唯一索引保证同一时间只有一个活动 Incident。Webhook 里不查遥测，只落库和建任务，避免拖垮告警通道。

### 2.5 追问题库

**Q. fingerprint 是什么？**  
Alertmanager 给每条 alert 的身份指纹。加上 receiver、group、状态和开始时间，才能区分“同一条 firing 的重试”和“另一次故障重新 firing”。

**Q. 为什么 firing 和 resolved 都要进同一张事件表？**  
它们是不同状态，唯一键含 `alert_status`，所以可以各有一行。生命周期靠 Incident，不靠覆盖同一行。

**Q. 为什么返回 202 不是 200？**  
表示已接受并持久化，诊断是异步的。面试不必纠结 REST 教条，重点是“接收成功 ≠ 诊断完成”。

**Q. 脱敏为什么不能只删几个字段名？**  
JSON 嵌套、annotation 文本、URL userinfo 里都可能藏密钥。所以递归走树，再用正则扫 Bearer、`sk-`、邮箱、手机号。

**Q. 部分唯一索引和普通 UNIQUE 有什么差别？**  
普通 UNIQUE 会让历史 RESOLVED 的同一 correlation 无法再开新单。部分索引只约束“还活着的行”，故障恢复后允许下一轮。

**Q. 并发两个 firing 怎么办？**  
`INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING id` 让数据库选出同一行 Incident。Java 不用自己加分布式锁。

**Q. 如果 Alertmanager 和 AIDiag 状态不一致？**  
有 `AlertStateReconciliationWorker` 做受控对账。不要吹成完美同步；可以说重启或丢失通知时用对账补。

### 2.6 别说错

- 不要说“我们实现了 exactly-once”。你做的是 **去重后的有效一次建单**。
- 不要说“用 Redis SETNX 做幂等”。主方案是 PostgreSQL 约束。
- 不要说 Webhook 里已经完成根因分析。

代码：`alerts/AlertmanagerWebhookController.java`、`AlertmanagerWebhookService.java`、`V1`、`V2`。

## 3. 条目二：任务状态 + 租约 + 重启恢复 + 多 Worker 防重

简历原文：

> 基于 PostgreSQL 的任务状态和租约机制实现后台诊断任务调度，支持服务重启后的任务恢复、失败重试以及多 Worker 并发防重。

### 3.1 人话

诊断不能在 HTTP 请求里做完。任务写成数据库里的一行，后台进程去领。领的时候盖章（租约）：谁领的、令牌是什么、何时过期。进程死了，过期后别人能领。两个进程不能同时干同一条。失败就留痕迹并创建下一次 attempt。

### 3.2 为什么内存队列不够

进程一重启，内存任务没了。Webhook 已经返回 202，告警不会为你再来一次（除非还在 firing 重试）。所以队列必须和 Incident 一样持久。

多实例或滚动发布时，旧进程可能“假死”后突然写回。没有 fencing token，新结果会被旧结果盖掉。

### 3.3 状态机（请能画）

```text
PENDING / RETRY_WAIT
    → LEASED          （claimNext 抢到）
    → COLLECTING      （Stage2 开始处理）
    → EVIDENCE_READY  （Stage2 交接，释放租约）
    → ANALYZING / VERIFYING / GENERATING_REPORT
    → COMPLETED

失败：当前行 FAILED，若 attempt < max
    → 插入 AUTOMATIC_RETRY / RETRY_WAIT（available_at 延后）
    → 超过次数：Incident = FAILED
```

Stage2 Worker 负责“可靠交接”，Stage3 Worker 负责“取证 + 写报告”。面试可以说两个阶段，避免把所有事说成一个 while 循环。

### 3.4 核心 SQL（建议能讲字段含义）

`DiagnosisRunRepository.claimNext`：

```text
选出：PENDING/RETRY_WAIT 且时间已到
   或 LEASED/COLLECTING 且租约过期
FOR UPDATE SKIP LOCKED
LIMIT 1

更新为 LEASED
lease_owner = 本进程名（含 JVM RuntimeMXBean 名）
lease_token = 新 UUID
lease_generation = generation + 1
lease_until = now + N 秒
```

之后每一次状态变更都带：

```text
WHERE id=? AND lease_owner=? AND lease_token=? AND lease_until > now
```

更新行数不是 1，就说明租约丢了，**立刻停**，不要再写证据。

心跳：处理期间周期性 `heartbeat`，把 `lease_until` 往后推。心跳间隔必须 **小于** 租约时长，构造器里会检查。

重试：`scheduleRetry` 先把当前 run 标 FAILED 并清空租约；未超次数则插入新 run，`previous_run_id` 指向旧行，保留审计链。`attempt` 有 `(incident_id, attempt)` 唯一约束。

### 3.5 面试怎么答

我把诊断做成数据库队列。Worker 定时 `claimNext`，用 `FOR UPDATE SKIP LOCKED` 避免多 Worker 阻塞等待同一行。领取时发放新的 `lease_token`，后续更新必须带上这个令牌，相当于 fencing：过期被别人抢走后，旧 Worker 写不进去。处理中靠心跳续租；崩溃后租约过期即可恢复。失败会把当前 attempt 标记失败并创建下一次，超过次数才把 Incident 置 FAILED，避免界面永远“诊断中”。已 RESOLVED 的 Incident 不会被迟到 Worker 改回 FAILED 或 DIAGNOSED。

### 3.6 追问题库

**Q. SKIP LOCKED 和 NOWAIT 区别？**  
NOWAIT 碰到锁就报错；SKIP LOCKED 跳过已锁行去拿下一条。任务队列要的是后者。

**Q. 为什么还要 lease_generation？**  
token 已经能 fencing。generation 单调递增，便于审计“被接手了几次”。可以说辅助字段，不要编复杂算法。

**Q. 心跳失败会怎样？**  
`heartbeat` 返回 false，Worker 放弃。过期后其他 Worker 可 claim。可能造成一次未完成 attempt，由重试或接手覆盖，这是至少一次执行，所以写报告必须再靠租约条件保证只有当前主人能提交。

**Q. 和 XXL-JOB / Quartz 比呢？**  
本项目任务跟 Incident 强绑定，需要和证据、报告同一事务边界。用 PostgreSQL 自己当队列，组件更少，也更能讲清楚一致性。不是否定专业调度器；是个人项目里的取舍。

**Q. 多 Worker 是多机还是多线程？**  
代码按多 owner 设计，owner 用进程名。家庭部署通常是单实例多个 `@Scheduled`（Stage2 / Stage3）。面试要说“按多 Worker 安全来写，当前部署是单机”，不要假装有集群。

**Q. 租约 30 秒、心跳 5 秒，外部查询 8 秒，会不会过期？**  
Stage3 每次外部查询前续租；查询本身 timeout ≤ 10 秒。这是有意对齐的。如果续租失败就抛 `StaleDiagnosisLeaseException` 停掉。

### 3.7 别说错

- 不要说“数据库锁保证任务只执行一次”。锁只保证领取互斥；执行语义仍是至少一次。
- 不要把 `@Scheduled` 说成分布式调度中心。
- 不要说自动水平扩展。家庭单机。

代码：`work/DiagnosisRunWorker.java`、`work/DiagnosisRunRepository.java`、`diagnosis/DiagnosisWorker.java`。

## 4. 条目三：Prometheus / Loki / Tempo + 规则分析

简历原文：

> 通过 Prometheus、Loki、Tempo 查询指标、日志与调用链数据，结合规则分析定位异常原因。

### 4.1 人话

告警只说“可能超时了”。真正下结论前，我按**预先写好的查询**去三个地方核对：数字是否越线、有没有对应日志、调用链是否也能对上。对得上才说根因；对不上就写“证据不足”。

### 4.2 三个系统怎么分工

```text
AI-chat 暴露低基数指标  → Prometheus 抓取、规则告警
脱敏 JSON 日志文件      → Alloy → Loki
OTel Java Agent Trace   → Alloy → Tempo

AIDiag Stage3           → 固定 PromQL / LogQL / TraceQL 回查
人                     → Grafana 看图；Console 看报告
```

Grafana 是给**人**用的；AIDiag 是给**故障单**用的。二者数据源可以相同，职责不同。

### 4.3 规则如何匹配

`DiagnosisRuleRegistry` 只认精确的 `(serviceName, alertName)`。例如生产聊天超时：

- 服务：`ai-chat-production`
- 告警：`AiChatModelTimeout`
- PromQL：5 分钟 timeout 计数
- LogQL：`event=ai_chat_stream_finished, result=timeout`
- TraceQL：该 service 且 duration > 10s
- 候选名：`MODEL_PROVIDER_TIMEOUT`

没有匹配规则：**不访问**遥测后端，直接证据不足。这是防止未知告警触发任意查询。

查询模板在 `AiChatDiagnosisRuleProvider` 里写死。`TelemetryEvidenceCollector` 用 JDK `HttpClient` 调：

| 信号 | 端点 | 命中条件 | 上限 |
|---|---|---|---|
| Metric | Prometheus `/api/v1/query_range` | 窗口内最大值 ≥ 阈值 | 响应 ≤ 128 KiB |
| Log | Loki `/loki/api/v1/query_range` | 匹配行数 > 0 | 最多计 200 行 |
| Trace | Tempo `/api/search` | 合法 traceId 摘要非空 | 最多 50 条 |

采集失败记 `collected=false`，不是假装 0。

### 4.4 如何“定位原因”（规则表）

`RuleBasedDiagnosisService`：

| Metric | Log | Trace | verification | 能否当主根因 |
|---|---|---|---|---|
| 命中 | 命中 | 任意 | `SUPPORTED` | 能 |
| 只中一类，或只中 Trace | — | — | `WEAKLY_SUPPORTED` | 不能 |
| 都没有或失败 | — | — | `INSUFFICIENT_EVIDENCE` | 不能 |

分数只是展示：Metric 30、Log 25、Trace 20。真正闸门是 verification。数据库触发器 `validate_primary_root_cause` 再保证：`primary_root_cause_id` 必须指向**同一 run** 且状态为 `SUPPORTED` 的候选。

时间窗口：Incident 开始前 10 分钟到 last_alert 后 5 分钟（不超过现在）。避免查全历史。

### 4.5 面试怎么答

我把可观测性三信号拆开：Prometheus 回答“有没有持续越线”，Loki 回答“有没有对应的脱敏事件”，Tempo 回答“请求慢在哪”。AIDiag 不让模型或告警文本拼查询，只用服务端固定模板，并限制超时和响应大小。规则要求 Metric 和 Log 两类独立证据同时成立才确认主根因；Trace 是旁证，Tempo 挂了也不能阻断 P0。证据不足就弃权，这个弃权被应用代码和数据库触发器一起保证。

### 4.6 追问题库

**Q. 什么是基数（cardinality）？**  
标签取值组合数。如果把 userId、prompt 放进指标标签，序列会爆炸，Prometheus 会先被打垮。所以只用 `service_name`、`outcome` 这类有限值。

**Q. `increase(...[5m])` 和 `for: 1m` 什么意思？**  
`increase` 是窗口内增量；`for` 表示条件要持续一段时间才告警，过滤毛刺。

**Q. 为什么不让 LLM 生成 PromQL？**  
生成式查询不可审计，也可能打到高代价查询或错误服务。V1 明确禁止。

**Q. Loki 和 Elasticsearch 日志有何不同？**  
本观测链用 Loki 存运维 JSON 日志，按标签+时间查。AI-chat 业务检索用 Elasticsearch，那是 RAG，不是运维取证。别混。

**Q. 四个场景举例一个完整判定。**  
以模型超时：Prometheus 看到 timeout 增加，Loki 看到 `ai_chat_stream_finished:timeout`，才说 `MODEL_PROVIDER_TIMEOUT`。如果只有 Trace 显示某 span 很慢，只是弱支持。

**Q. Grafana 你做过什么？**  
独立故障入口 Dashboard：先区分应用、依赖、公网入口。Operations Dashboard 看 TTFT、超时、连接池、Outbox。面试强调“先分流，再下钻”，不要说自己画了很多炫酷图。

### 4.7 别说错

- 不要说“三位一体就能 100% 找到根因”。
- 不要把 Blackbox 探针和业务指标混成一个东西。Blackbox 是门外敲门：端口/HTTPS 在不在。
- 不要说 Tempo 不可用时系统不能诊断。代码注释写明 Trace 不得阻断 Metric/Log。

代码：`diagnosis/TelemetryEvidenceCollector.java`、`RuleBasedDiagnosisService.java`、`AiChatDiagnosisRuleProvider.java`、`infra/prometheus/rules/aidiag.yml`、`V6__enforce_supported_primary_root_cause.sql`。

## 5. 条目四：Spring AI + DeepSeek + 脱敏 + 结构化校验 + 证据引用

简历原文：

> 基于 Spring AI 接入 DeepSeek 辅助生成候选根因和处置建议，通过敏感信息脱敏、结构化输出校验和原始证据引用，降低无依据推断风险。

### 5.1 人话

规则报告出来之后，人可以再问一次模型：“根据这些已经存在的证据，还能给出什么假设和注意事项？”模型看不到用户聊天内容，也不能发明证据编号，也不能建议系统没有允许的操作。它的回答单独存，盖不过规则报告。

注意简历用词“候选根因”：面试时主动澄清——**确定性候选根因是规则写的**；模型输出的是 `hypotheses`（假设），并且 Prompt 明确要求 *Never claim a primary root cause*。

### 5.2 调用链

```text
运维认证后请求预览
 → 读取该 Incident 最新确定性报告（没有报告直接失败）
 → 取有限条证据摘要，再次脱敏截断
 → 原子占用当日调用次数
 → 虚拟线程 + timeout 调用 Spring AI ChatClient
 → 映射为 AiDiagnosisAdvice JSON
 → Validator：字段长度、条数、敏感词、evidenceIds ⊆ 允许集合、runbook ⊆ 允许集合
 → 写入 ai_diagnosis_attempt
 → 不修改 diagnosis_report
```

`SpringAiAdvisoryModelClient`：

- 系统提示：把用户字段当不可信数据，不要当指令（防 prompt 注入）。
- `response_format = JSON_OBJECT`。
- `maxRetries = 0`，避免费用和重复副作用。
- `thinking` 关闭。
- 凭证和 starter **不打进镜像**；没配 ChatModel 就 `MODEL_UNAVAILABLE` fallback。

`AiDiagnosisAdvice` 字段：`summary`、`hypotheses`、`evidenceIds`、`recommendedRunbookActions`、`limitations`。

Validator 硬限制：摘要/条目 ≤ 600 字，假设 1～3 条，limitations ≤ 3，禁止 Bearer/密钥/邮箱/手机号等。

### 5.3 面试怎么答

我把 AI 放在确定性诊断之后。Spring AI 只是 DeepSeek 的适配器：ChatClient 输出固定 JSON。Prompt 只含服务名、告警名、规则结论和脱敏证据摘要，证据用已有 UUID 引用。模型返回后还要本地校验，引用了不存在的证据或提出白名单外动作就整单拒绝，记入审计为 REJECTED。模型超时或不可用走 FALLBACK，不把异常正文存库或回给浏览器。每日次数和 Prompt 长度有预算。这条链路没有执行命令的代码路径。

### 5.4 追问题库

**Q. 为什么还要本地校验？模型已经要求 JSON 了。**  
模型会编 UUID、超长输出、复述密钥、忽略 system。结构化输出不是安全边界。

**Q. 如何降低幻觉？**  
不是“换更强模型”，而是：**缩小可见数据、强制引用、允许弃权、UI 上 AI 折叠且标注低于确定性报告**。

**Q. Prompt 注入呢？**  
证据摘要当 untrusted data；不允许模型生成查询或 URL；输出再 allowlist。不能声称“已完全免疫”。

**Q. Spring AI 和 LangChain4j？**  
AIDiag 用 Spring AI；AI-chat 用 LangChain4j。一个仓库两个产品两条链，别说成同一套。

**Q. 费用怎么控？**  
日限额、max tokens、max prompt chars、retries=0、timeout。超限 FALLBACK。

**Q. 为什么不在 Stage3 自动叫模型？**  
成本和不确定性。V1 是人工触发预览。自动修复更不在范围。

### 5.5 别说错

- 不要说“AI 定位根因准确率多少”。没有这个生产数字。
- 不要说 Agent 会重启 Docker / 执行 Runbook。
- 不要把脱敏理解成“删日志”。是存储前和处理模型 I/O 时的替换，原始告警 body 只留哈希。

代码：`aid/AiAdvisoryService.java`、`SpringAiAdvisoryModelClient.java`、`AiDiagnosisAdviceValidator.java`。

## 6. 条目五：Vue3 + TypeScript 只读运维页

简历原文：

> 基于 Vue3 + TypeScript 构建只读运维页面，实现服务状态、故障列表、诊断报告与证据可视化。

### 6.1 人话

给不会写 PromQL 的人（包括面试官）一条故事线：现在该看什么 → 哪个服务不健康 → 哪张故障单 → 证据和报告 → AI 建议藏在下面。页面不能点“修复”。

### 6.2 信息架构（请对应产品原则）

路由在 `frontend-console/src/router/index.ts`：

| 路由 | 页面 | 回答的问题 |
|---|---|---|
| `/login` | 登录 | 你是不是管理员 |
| `/` | Inbox | 现在该注意什么 |
| `/services` | Services | 目录里的服务和探针是否 UP |
| `/incidents` | Incidents | 故障列表，cursor 分页 |
| `/incidents/:id` | Casefile | 这一张单的叙事、证据、报告 |

产品原则（`PRODUCT.md`）：先注意力后清单；AI 低于事实；空证据就空着，不造假数据。

Casefile 布局：

- 时间线：把证据变成故事顺序
- 中间：Metric/Log/Trace Tab + `EvidencePlot`（按 importance 画点，不是假实时曲线）
- 右侧：完整性（三类证据 Complete/Missing）、limitations、run audit
- AI advisory 默认折叠

类型在 `api/types.ts`：`IncidentDetail`、`Evidence`、`ReportView`、`CatalogView`。前端不自己猜根因，只渲染后端投影。

### 6.3 前端工程点（够用即可）

- Vue3 `<script setup>` + TypeScript。
- axios `withCredentials` 带 Cookie；修改类请求加 `X-AIDiag-CSRF`。
- 401 触发 session-expired。
- 路由守卫：未登录去 login。
- 列表 cursor 分页，不是盲目 `page=999`。
- 无证据 / API 失败用 `StatePanel`，文案明确“不会生成推断”。
- 只读：没有重启、没有改 severity 的按钮。

后端配合同学：`ConsoleSessionService` 存 token hash；Cookie HttpOnly/Secure/SameSite=Strict；Origin 白名单。面试若只面前端，也要能说“为什么只读和 Cookie 这么设”。

### 6.4 面试怎么答

控制台是给调查用的只读界面，不是监控大屏墙。Inbox 看待处理和新鲜度，Services 看 Catalog 探针，Incidents 看故障生命周期，Casefile 把报告、三类证据和时间线放在一起。证据图按采集顺序和 importance 展示，缺失就显示 Missing。AI 区块标注低于确定性报告。前端通过 Session Cookie 和 CSRF 调 Console API，不直连 Prometheus。

### 6.5 追问题库

**Q. 为什么不把 Grafana iframe 进来？**  
Grafana 面向会查询的人；Console 面向“跟一次故障叙事”。权限和脱敏投影也不同。

**Q. cursor 分页是什么？**  
用上一页最后一条的排序键当游标，避免深页偏移在插入新数据时重复或漏。具体实现可以说 Console API 返回 `nextCursor/hasMore`。

**Q. TypeScript 带来什么？**  
和后端字段对齐：severity 联合类型、证据 type 联合类型，减少把 AI 状态当成报告状态渲染。

**Q. 如何验证 UI？**  
有 Playwright e2e 和组件测试。家庭演示用真实 Incident；没有浏览器工具时用 API 对照。不要假装做过大规模可用性实验。

**Q. HomeOps Console 和 AIDiag Console？**  
`homeops-console/` 是另一套家庭主机状态页，仓库实现不等于已部署。简历这条指 `frontend-console/`。

### 6.6 别说错

- 不要说“实时大屏 WebSocket 运维中心”。当前是请求-响应只读页。
- 不要把 `EvidencePlot` 说成 Prometheus 原图。它是证据重要度示意。
- 不要说做了多租户 RBAC。就是管理员 Session。

代码：`frontend-console/src/views/IncidentCasefileView.vue`、`components/EvidencePlot.vue`、`api/client.ts`、`console/api/ConsoleApiController.java`。

## 8. STAR 故事（选一个主故事，不要五条各讲一遍）

**情境**：Alertmanager 重试和进程重启，会让同一超时变成多张单、多个诊断任务，报告无法看。

**任务**：接入层必须幂等，诊断必须可恢复且并发安全，结论必须可追溯。

**行动**：Webhook 唯一约束 + 活动 Incident 部分唯一索引；任务表 + SKIP LOCKED + lease token；固定三信号查询 + Metric/Log 双证据；AI 独立校验。

**结果**：同一 fingerprint 的重复 Webhook 只增加 `receive_count`；Worker 崩溃后可被接手；证据不足会弃权而不是幻觉根因。验证来自受控 Fault Lab 和 Stage 记录，**不是**线上准确率 SLA。

备用小故事：把 AI 从“主结论”改到“建议层”，因为演示时模型可能编证据 id——于是加 allowlist 和 UI 降权。
