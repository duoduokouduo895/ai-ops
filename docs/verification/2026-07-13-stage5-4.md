# Stage 5.4 独立故障入口验证记录（2026-07-13）

## 结论

Stage 5.4 的主救援入口已从 AI-chat Admin 中拆出。云端初始 release `20260713-stage5-4-3` 已运行独立 Blackbox 探针和 Grafana Dashboard，当前资源修复 release 为 `20260713-stage5-4-grafana1536-1`；AI-chat Admin 只保留为服务存活时的辅助入口。该设计能覆盖 AI-chat JVM 未启动和中间件网络不可达，但不能覆盖整台 GCP 主机或同机监控平面失联。

## 已验证内容

- AIDiag 未认证只读 API 返回 `401`，文件型凭据认证的 shadow summary 返回 `200`，越界分页返回 `400`，响应 JSON 字段完整；浏览器不持有该凭据；
- Blackbox Exporter `v0.28.0` 使用 digest 固定镜像，未映射宿主机端口；Prometheus 与 Blackbox 同样不直接暴露公网；
- `application`、`mysql`、`redis`、`rabbitmq`、`elasticsearch`、`nacos` 六个 `probe_success` 序列均存在且当前为 `1`；
- Grafana 已 provision `ai-chat-break-glass`（“AI-chat 独立故障入口”）和原 Stage 5 Operations Dashboard；
- Prometheus 的既有 bind mount 保持不变；Grafana 的 provisioning 与 dashboard bind mount 已确认指向 `/opt/aidiag/releases/20260713-stage5-4-grafana1536-1`，不再引用稳定软链接的旧目标；
- AIDiag 本地与云端构建均包含真实 Spring Bean 装配测试，防止只通过直接构造对象而漏掉容器启动错误。
- AI-chat candidate `20260713-stage5-4-candidate-1` 已发布且 health 返回 `200`；未认证 ADMIN BFF 返回 `401`，候选容器使用文件 Secret 访问 AIDiag summary 返回 `200`，应用外部探针保持 `1`；DNS 与 Nginx 未修改。

## 发布中发现并修复的问题

1. 首次激活时 `ReadApiAuthenticator` 存在两个构造器但未明确注入入口，单元测试通过、生产 Spring Context 启动失败。健康门禁阻止切换；随后增加 `@Autowired` 和 `ApplicationContextRunner` 回归测试。
2. 原回滚流程恢复了 release 软链接，但共享的本地镜像标签仍指向失败版本，导致旧目录启动新镜像。已改为回滚时从旧 release 重建镜像。
3. Compose 曾以稳定 `current` 软链接作为 project directory，Docker 继续挂载旧 release 的 Prometheus/Grafana 配置。已改为使用不可变真实 release 路径；当前云端 Prometheus/Grafana 已强制重建并验证新配置生效。
4. `size=101` 最初被 Bean Validation 拦截后返回 `500`。已移除 Controller 级 AOP 校验，使用 Spring MVC 原生方法校验，并增加“返回 400 且不查询数据库”的测试；云端补丁 release 已验证返回 `400`。
5. Grafana 13.1.0 在 `384 MiB` 容器上限下发生重启，浏览器加载核心面板模块时统一显示 `Error loading`。资源修复 release 将 Grafana 上限提升为 `1536 MiB`，仅重建 Grafana；发布后 `/api/health` 返回 `database: ok`，容器限制为 `1610612736` bytes、重启次数为 `0`，延迟复核时使用约 `157 MiB`，其他 AIDiag 容器未被连带重建。

## 边界与后续

- TCP 探针成功仅表示 DNS、路由和端口连接成功，不证明账号密码、协议命令、数据正确性或性能正常；
- Alloy 当前主要读取应用文件日志。JVM 若在 logger 初始化前失败，仍需从受限 Docker 日志采集链补启动证据；不得直接向业务容器开放原始 Docker socket；
- Grafana 与被监控项目同机。如果主机、Docker daemon、磁盘或主机网络整体故障，需要外部 uptime/GCP Monitoring 产生第二条独立信号；
- Admin BFF 已在私有候选部署，前端源码已完成本地构建但未发布到 Cloudflare Pages；仍需使用真实 ADMIN 登录完成一次端到端验收。它不是启动失败时的救援入口。
- Grafana 镜像未定义 Docker `HEALTHCHECK`，当前发布门禁使用容器运行状态和 `/api/health`。启动日志仍会报告缺少可选的 plugin/alerting provisioning 目录，以及只读文件系统阻止 Elasticsearch/Zipkin 后台安装器写入；这些不影响当前核心 Dashboard，但后续应单独收敛日志噪声并补显式健康检查。
- 本次为避免连带重启，仅将 Grafana 挂载迁移到资源修复 release；其他运行中服务仍可能挂载内容相同的 `20260713-stage5-4-3`。在下一次完整发布统一迁移前不得删除该旧 release。
